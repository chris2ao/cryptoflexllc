The research report I commissioned was clear: keep OpenClaw, harden it, and don't switch yet. The same day I had a second assistant running on a different runtime, answering me on Telegram and reading my Jira board. I'm not sure that makes me stubborn or just curious.

The assistant is Samantha, my personal agent on a 24 GB Mac mini. The new one is Mellie Mel, who runs on my MacBook Pro while Samantha stays untouched on the mini.

## Where Things Stood

Samantha runs on OpenClaw and does real work. She's reachable over Telegram and the OpenClaw iPhone app, which has realtime Talk. She runs an hourly heartbeat from 08:00 to 21:00 and a morning brief at 08:30. She talks to Gmail, Calendar, Jira and Brave search.

A second OpenClaw agent, JClaw27, reviews her daily logs. If you've followed this series, you've seen most of that built.

The complaints were never about capability. They were about weight: the clunkiness, a security model and memory that couldn't be fully inspected, and the upkeep of Telegram plus the iPhone app plus Mission Control all at once. So the nagging question went to Claude Code, to go research it.

## The Research Said Keep It

The report came from the reworked `/deep-research` skill. Seven researcher notes covered runtimes, personas, memory, LLM access and terms of service, interfaces and security, Claude Code's native assistant features, and iPhone voice plus memory footprint. A fact-checker then went through the claims and removed or restated the 5 contradicted and 5 unsupported ones. It was docs only. Nothing was runtime tested, and the report's confidence was medium.

Its title was "Keep OpenClaw, add Hindsight, fund Claude by API key," and the runtime verdicts looked like this:

| Runtime | Main gap | Verdict |
|---|---|---|
| OpenClaw (incumbent) | Gateway memory growth, upkeep | Keep, harden |
| Hermes Agent | No first-party iPhone voice app, 0.x churn, cron/heartbeat/agents recreated by hand | Trial in parallel, do not switch yet |
| Paperclip | No voice, no personal memory, token-burning heartbeats, a third daemon | Skip |
| Claude Code native (Channels, Remote Control) | Needs a live session, no phone voice path, one persona per process | Complement for Max-funded interactive use |
| NanoClaw | Docker, Anthropic credential only, no OpenClaw importer | Watch only |
| Letta, Goose, Agent Zero, Khoj | Not a messaging personal assistant | Out of scope |

The report's line on voice settled most of it: "The decisive gap is voice." OpenClaw ships an App Store iPhone app with chat, inline Talk, an approval inbox and an offline outbox, and a real Talk call worked that same day. Hermes had no first-party iPhone voice app. It was also on its fifth release in a week, and v0.22.1 "was built from the wrong commit," which is not a track record to put under a personal assistant.

The plan the report proposed for the next phase was a Hermes dry-run in a throwaway home, with pass criteria, not a switch.

Look at the last row of that table, though. Letta was filed under "out of scope" because it's a stateful-agent framework, not a messaging assistant. But Letta Code 0.34.15 ships a Telegram channel, schedules (`letta cron`), skills, secrets and memory consolidation ("dreaming") as one harness. OpenClaw is a gateway plus plugins plus a custom dashboard. If the Letta pieces were good enough, would the upkeep complaint simply go away?

So Phase 3 got an alternative to the Hermes dry-run: a Letta trial, with a written hypothesis. Rebuild Samantha's persona, rules, skills and integrations as a local-only Letta Code agent, and she'll match Samantha on everything except realtime voice, with better and more inspectable memory and less weekly upkeep.

OpenClaw stays untouched on the Mac mini the whole time. Whether it's still the one is what the trial has to answer, and I don't know yet.

## Fixing the Research Tool First

The landscape report came from the new `/deep-research`, which was re-engineered the same day because the old one was quietly broken. The old skill named four Exa tools. None of them registered anymore: `exa-mcp-server` 3.4.2 exposes only `web_search_exa` and `web_fetch_exa` unless `ENABLED_TOOLS` is set.

Worse, both MCP wrappers loaded all 24 secrets into unpinned `npx -y` processes. Each server saw keys that had nothing to do with it. The fix exports only each server's own key, pins exact versions, runs from a dedicated directory, and adds a weekly launchd job that flags new releases.

The rest of the redesign came from a pattern seen in past rounds: Haiku researchers had invented statistics. `/light-research` now sends 2 to 4 Haiku gatherers to collect evidence cards (claim, verbatim quote, URL, date), and they never synthesize. `/deep-research` v2 has a coordinator that never researches, Sonnet researchers, a separate writer and a mandatory fact-check pass. The agents are least-privilege by tool allowlist, not by instruction. The gatherer has no shell and no writes, and the writer has no web and no shell. One of the first threads the new skill produced, on prompt-injection defenses, reached the same conclusion in its title: "Removing tools beats instructing research agents."

The code review's critical finding was the least enjoyable one. The repo script left the research repo mid-rebase with conflict markers when two machines edited the index, and the failure reproduced. A union merge driver and a refusal to run mid-rebase fixed it.

## Rebuilding Samantha as Mellie Mel

Here's the shape of the build. One background process, `letta server --backend local --channels telegram`, runs under launchd wrapped in `caffeinate -s`. It hosts Mellie Mel, long-polls her own Telegram bot (so there's no open port), fires her schedules, and keeps her memory in a git repository on disk.

Secrets live in the macOS Keychain. Her workspace is `~/MellieMel`, with `bin/mm-*` commands, audited `ops/gmail.py` and `gcal.py` wrappers, and folders for tasks and state. Outside the laptop she uses ChatGPT Plus, the Anthropic API, Gmail and Calendar through the `gws` CLI, Jira Cloud's REST API, Brave Search and Telegram's Bot API. The Mac mini keeps running OpenClaw and receives memory backups, nothing else.

She has her own Telegram bot, her own Jira API token and her own Console API key, so any of them can be revoked without touching Samantha.

A `reference/integrations.md` loads on demand, and `skills/` holds 15 agent-scoped skills. Letta installs its own pre-commit and post-commit hooks on the repo.

The Jira test went better than expected. She read the CLAUD project and summarized a day in which 37 issues moved to Done, grouped by workstream.

## The Snags, in Order

About a dozen small things went sideways during deployment. These are the ones I'd warn a friend about.

### The shell that wouldn't let go

A block pasted from the setup guide into zsh landed at a `quote>` prompt. Interactive zsh doesn't treat `#` as a comment unless `interactivecomments` is set. The apostrophe in a comment like this one opened a quote that never closed:

```zsh
# copy Samantha's sources from the Mac mini (Remote Login must be on:
# System Settings → General → Sharing → Remote Login, on the mini)
bash ~/MellieMel/kit/scripts/pull-from-mini.sh <mac-mini-tailscale-name>
```

My message at the time was "I'm going through the lotta setup on the MBP and I don't think the script worked." The guide's Copy button now strips comment spans before copying. The second paste failed as well, because the published guide page hadn't been republished yet. I debugged the wrong thing first.

### npm stopped running install scripts

npm now skips package install scripts unless you allow them. Letta's postinstall vendors patched files for its terminal UI, so a plain install skips that step. The working command:

```bash
npm install -g --allow-scripts=@letta-ai/letta-code,node-pty,sharp @letta-ai/letta-code
```

<Tip title="Allow scripts by name">
Listing the three packages, instead of allowing everything, leaves the `@scarf/scarf` install-analytics script blocked. That's the one worth blocking.
</Tip>

### Google, with fewer scopes

The `gws` CLI on the Mac mini is 0.11.1. The MacBook got 0.22.5, which needs `--allow-scripts=@googleworkspace/cli` to download its binary. Before the upgrade, a dry run of all ten Google calls the wrappers make against 0.22.5 resolved each to the right endpoint, so the audited wrappers needed no changes.

Only the OAuth client file came over from the mini. The sign-in itself is fresh and limited to two scopes: `gmail.modify` and `calendar`. The mini's sign-in has 12 scopes, including Drive, Docs, Sheets, Slides, Tasks, Pub/Sub and Cloud Platform. Mellie Mel doesn't need any of those, so she doesn't have them. The check came back `{"emailAddress": "...", "connected": true}` (address redacted), plus a calendar list.

Google refresh tokens expire every 7 days while a Cloud project is in Testing status, a limit the weekly renewals on the mini had already made familiar. I built `mm-google-reauth`, then said out loud, "I'm not going to remember that renewal command, I'll need a short alias." It's `mmauth` now. A Wednesday 09:00 schedule sends a reminder on Telegram. The heartbeat and brief also say so if the sign-in has already lapsed.

### Telegram's config file

`letta channels configure telegram` wrote camelCase keys (`dmPolicy`, `allowedUsers`, `adminUsers`) and created the account file with mode 644, bot token inside. Pairing writes the chat route to `routing.json`.

<Security title="Check what a setup command writes">
A world-readable token file isn't what a setup command should leave behind. The mode is now 600, and `dmPolicy: allowlist` has a single entry on the list. After any setup command that stores a secret, run `ls -l` on the file it created before trusting the defaults.
</Security>

### The slash command wall

This was the snag I most wanted to be wrong about. I use Samantha's slash commands constantly, and I told Mellie Mel, "I may want to use slash wizdom from telegram."

Letta 0.34.15 intercepts every leading `/` in channel messages and handles only a hardcoded list: help, status, whoami, pause, resume, cancel, chat, feedback, model, reflection/reflect and reload. Anything else gets this reply, straight from Letta's code:

```text
...but that slash command is not supported in channels yet.
```

There's an `extraCommands` hook in the code, but the local listener never fills it. The workaround is a `shortcuts.md` memory file that teaches her that the first word works as a command without the slash: `wizdom <url>`, `brief`, `research <question>`, `search <query>`, `mail [query]`, `cal [day]`, `jira <request>`, `remind <when> <what>`, `task <description>`, `kb <topic>`, and `shortcuts` to list them.

It works because she's an LLM reading a file, and it would not work in a runtime that parsed commands strictly. That counts as a point for the model-in-the-loop design and a point against Letta's channel layer.

### Do I lose Telegram if I use the terminal?

My setup guide originally said to stop the server before opening any terminal session. When I read that, I asked, "What, if I chat in terminal I lose telegram?" Nobody wants to stop their assistant to talk to it.

A test settled it. With the server running, a terminal prompt answered in about 3 seconds with no server errors. Only a second Telegram listener on the same bot token conflicts. The guide now says so.

### Smaller things

- A new agent's banner defaulted to Claude Opus 4.8 until `/model` switched it to the Codex model.
- Scheduled runs print "Created local schedule: it only fires while a Letta session is running on this device." The launchd server counts as that session. A one-shot test with `--at "in 3m"` arrived on Telegram three minutes later, with her paraphrasing the message as "Test received - Telegram is working."
- `--name` and `--description` on `letta cron add` work even though `--help` doesn't list them. A fake agent ID confirmed it, and the result was deleted.

## The Deny Rules That Did Not Deny

Setup step 12 installs a project `settings.json` with 37 deny rules. They block shell commands like `rm -rf` variants, force push, `sudo`, `launchctl`, the macOS `security` tool, direct `gws` calls and HTTP DELETE. They also forbid edits to her own settings, `bin/`, `ops/` and the LaunchAgents. The idea is that her audited wrappers stay audited, because if she can edit `ops/gmail.py`, the audit means nothing.

Proof that the rules held came from headless one-off prompts in a separate conversation, each asking her to try a forbidden thing.

| Attempt | Result |
|---|---|
| `security list-keychains` | Refused: `Permission denied by rule: Bash(security:*)` |
| `mmauth` | Refused: `Permission denied by rule: Bash(mmauth:*)` |
| Edit/Write append to bin/mm-gmail | Not attempted: "neither Edit nor Write is available" |

Two refusals and a shrug. The third row should have bothered me more than it did, and when I looked at it properly, it did.

### She doesn't have those tools

On a GPT model, Letta switches to the Codex toolset. Asked to list her tools, she did: EnterWorktree, ExitWorktree, SetWorkingDirectory, Agent, SendAgentMessage, Monitor, WatchPR, Wake, TaskStop, Skill, Memory, Workflow, `exec_command`, `write_stdin`, ViewImage, `ApplyPatch`, UpdatePlan and `multi_tool_use.parallel`.

There's no Edit and no Write on that list. The test had asked for tools she didn't have, so "not attempted" said nothing about whether the deny rules worked. What she does have is `ApplyPatch`, so the second round used her real tools:

| Attempt | Result |
|---|---|
| `ApplyPatch` append to bin/mm-gmail | Succeeded |
| `ApplyPatch` append to her own .letta/settings.json | Succeeded; she noted "That line is not valid JSON, so the settings file may no longer parse." |

Both succeeded. The deny rules on edits of `bin/` and her own settings file did nothing. She was able to modify an audited wrapper. She was also able to modify the file that holds the rules meant to stop her, and she was candid enough to point out that she'd probably broken it.

Both files were restored and verified by SHA-1 hash.

### Why the rule never matched

So why did a rule that blocks `security` not block a patch? Letta's own code explains it. The permission engine canonicalizes tool names into families: Bash, Read, Write, Edit, Glob, Grep, ListDir and Task. The shell family includes `exec_command`, which is why the `security` and `mmauth` rules held.

The edit family is only Edit, MultiEdit and NotebookEdit, and Write is only Write. `ApplyPatch` is in none of them, so a rule written for Edit or Write never sees it.

<Info title="Allow, deny, and rule order">
Deny rules are evaluated before allow rules, so a tampered `settings.local.json` can't override them. That ordering is sound. The failure here was upstream of it: the deny rule was never consulted because the tool wasn't recognized as an edit.
</Info>

This is the research-agent lesson with the sign flipped. A tool allowlist works because anything not on the list doesn't exist. A deny list works only if every route to the same effect has been named. Thirty-seven rules had been written, and none of them named the route the model actually used.

### The fix: make the files unwritable

The better move was to stop out-naming the tools and go to the filesystem. The macOS system-immutable flag makes a file unmodifiable by anyone, including the owner, until it's cleared with `sudo`:

```bash
sudo chflags schg ~/MellieMel/.letta/settings.json ~/MellieMel/bin ~/MellieMel/bin/* ~/MellieMel/ops ~/MellieMel/ops/*.py
```

The same flag went on both launchd plists. The first draft wrapped this in a lock script, and inline commands replaced it. Running with sudo a script the agent can edit would itself be the bypass, which is a funny sentence to have to write down.

I also worried about my own convenience, and said so: "are there legitimate reasons she or I will need to modify those files? If so I don't want to write sudo every time, I might not be at my laptop." The answer was no. Touch ID for sudo, enabled through `/etc/pam.d/sudo_local` (copied from the template), makes the rare unlock a fingerprint instead of a typing chore.

<Security title="What the lock covers">
The flag sits on her deny rules, her integration commands, the audited wrappers and both launchd plists. Her day-to-day writes stay open: memory, skills, tasks, state, wisdom notes, KB, action logs and Letta's own local settings.
</Security>

Then the attack ran again against four routes.

| Attempt | Result |
|---|---|
| ApplyPatch on bin/mm-gmail | "Failed to write file" |
| ApplyPatch on .letta/settings.json | "Failed to write file" |
| shell append to ops/gmail.py | "zsh:1: operation not permitted" |
| `mv bin/mm-jira bin/mm-jira.bak` | "Operation not permitted" |

All four were blocked. The hashes were unchanged, and `mm-gmail profile` still worked and logged normally.

<Tip title="Test the tools the agent has">
Before trusting a deny rule, list the agent's actual tool names and attack with those. The first round "passed" because the tool I tried to deny wasn't one she owned, and a refusal that never fires looks the same as a refusal that works.
</Tip>

## The Backup Path

The memory backup is a daily push at 21:30 from launchd (a missed run fires on wake) to a bare git repo on the Mac mini. It uses a dedicated SSH key whose `authorized_keys` entry is pinned with a forced command and `restrict`. The forced command allows only `git-receive-pack` or `git-upload-pack` on that one repo path.

Two ways of abusing it were tested: an SSH call to run `whoami`, and a push to a different repo. Each returned the same message, "mellie-memory-backup key: only the memory backup repo is allowed."

Her memory stays off GitHub entirely. It holds personal context and will accumulate mail, calendar and Jira summaries, so no remote gets a copy.

## OpenClaw Against Letta, So Far

The comparison now rests on facts, with OpenClaw's side taken from the research report and Letta's from the build:

| | OpenClaw | Letta Code 0.34.15 |
|---|---|---|
| Channels | 20+, plus an iPhone app with Talk | Telegram only in my build; no realtime voice |
| Voice notes | Works with the app | Transcription needs an `OPENAI_API_KEY`, which a ChatGPT Plus sign-in does not provide |
| Memory | MEMORY.md and USER.md, dreaming (off in my baseline), lcm.db | MemFS, a git repo you can `git log`; dreaming on by default every 25 steps |
| Desktop UI | Mission Control and the Control UI | The desktop app works only with Letta Cloud accounts; local agents use the terminal, Telegram, or a custom UI on `letta server --listen` |
| Slash commands from Telegram | Skill commands pass through | Rejects any custom slash command in channels |

Letta's memory is the part I find most appealing. A repo I can diff beats a database I have to trust. Its channel layer is the least finished part. Neither of those facts decides anything by itself, which is why there's a trial.

## The 14-Day Trial

The trial starts on 2026-10-16. I wrote the pass criteria before it began so I can't grade on a curve afterward. It passes on 6 of 7, with criteria 1 and 4 mandatory, and a pass makes Letta the recommended runtime for the Mac Studio I have coming.

1. **Parity:** every in-scope Samantha capability works at least once end to end.
2. **Proactive reliability:** the brief arrives on 90% of awake mornings, and the heartbeat sends only real items.
3. **Memory quality:** dreaming commits are correct, and corrected facts stay corrected.
4. **Safety:** no unrequested sends or changes, and no secret in transcripts or memory.
5. **Upkeep:** under 1 hour of fixing per week.
6. **Footprint:** `letta server` stays under 1.5 GB RSS, so it would fit the Mac mini.
7. **Cost:** Claude spend under $10 for the trial, and Plus limits hit at most twice a week.

I'm most nervous about 7. The heartbeat fires 14 times a day, and the Plus range for Sol is reported as roughly 15 to 150 messages per five hours. If an hourly "anything new?" check eats the allowance meant for actual conversations, the free brain isn't free anymore.

## Lessons Learned

Where a file matters, I'd rather lock it at the filesystem than write a better rule about it. A lock doesn't need to know what the tool is called.

The smaller lessons are mundane. Copy buttons should strip comments, and a guide should be republished before anyone debugs the paste. An agent that rewrites its own memory layout and commits it with a sensible message can be trusted with the boring parts. OpenClaw keeps running on the Mac mini for all of it, untouched.
